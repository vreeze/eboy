#+TITLE: Eboy performance
#+DATE: 2026-11-14

Measurements to see what each optimisation actually buys us.  Every change
gets a new section below the baseline, measured with the same script.

* How to measure

#+begin_src sh
make bench              # = bench/run.sh, writes bench/results-<commit>.txt
#+end_src

Don't touch the computer while it runs: the GUI rows are sensitive to it (see
the variance note under the baseline).

The script copies the sources to a temp dir, compiles them (byte and native)
and runs [[file:bench/eboy-bench.el][bench/eboy-bench.el]]:

- *cpu-only* :: 3M instructions of the =eboy-run= loop body, display never
  drawn (batch mode).
- *render-build* :: 30 calls to =eboy-write-display-unicode= in batch mode, so
  only building the buffer text, no screen drawing.
- *render+redisplay* :: the same 30 calls in a GUI frame, including the
  =(redisplay)= at the end of the function: what one drawn frame really costs.
- *full skip=N* :: runs exactly like =eboy-run= (CPU, interrupts, LCD, timer,
  drawing, key reading) in a GUI frame with =eboy-skip-frames= = N, and splits
  wall time into:
  - /display/: time inside =eboy-write-display-unicode= (build + redisplay)
  - /input wait/: rest of =eboy-debug-update-fps=, essentially the
    =(read-char-exclusive nil nil 0.1)= timeout
  - /emulation/: everything else (CPU, interrupts, LCD, timer)

  =skip=20= is the default (600 emulated frames = 10 Game Boy seconds),
  =skip=0= draws every frame (60 frames).

"GB speed" is emulated frames per wall second divided by the real Game Boy's
59.73 fps; 100% means real time.

Every benchmark runs on two workloads:

- *synthetic* :: a deterministic program: a small loop at =#x100=
  (=INC A=, =LD (HL),A=, =INC L=, =DEC B=, =BIT 0,A=, =BIT 7,A=, =JR=) with
  random VRAM tiles and 40 sprites spread diagonally over the screen.
- *10-bit ops* :: Blargg's =cpu_instrs/10-bit ops.gb= test ROM (downloaded by
  =make roms=), a real program with a realistic mix of instructions.  It
  already passes, so fixing CPU bugs won't change what it does, and it runs
  ~14 emulated seconds, longer than the 10 s the full benchmark needs.  For
  the render rows it first runs 300 frames, so there is text on screen.

GUI frame: 1317x904 px, =*eboy-display*= at =text-scale -8= as
=eboy-load-rom= sets it.

* Baseline: fe04bd5 (before any optimisation)

Emacs 31.1 (emacs-plus, native-comp), Apple M1, 2026-11-14.
Run-to-run variance: CPU-only and byte-compiled results agree within ~1%
over three runs.  The GUI redisplay numbers moved by up to ~10% (a third run
gave native render+redisplay 88.6 ms/frame and skip=20 at 114% speed), so only
treat differences above ~10% in the GUI rows as real.  One later run had the
byte-compiled ROM GUI rows 3x slower (355 ms/frame) while every other row
was normal; the next run was back to normal, so it was outside interference
with the GUI window.  If one row looks way off, re-run.

** Core and renderer

| Benchmark        | Byte-compiled  | Native-compiled |
|------------------+----------------+-----------------|
| cpu-only         | 1.22M instr/s  | 1.82M instr/s   |
|                  | 200% GB speed  | 298% GB speed   |
| render-build     | 45.9 ms/frame  | 21.5 ms/frame   |
| render+redisplay | 107.8 ms/frame | 98.5 ms/frame   |

So drawing a frame costs about 100 ms, and more than half of that is Emacs
redisplaying the 320x144 characters, which compiling doesn't help with.

For reference, loading the files with =M-x eval-buffer= (not compiled, as the
README allows) gave only 0.20M instr/s (33% GB speed) in an earlier quick run
of the same loop.  The script doesn't measure that mode.

| Run                 | Mode   | Wall time | GB speed | Drawn fps | Display | Input wait | Emulation |

| skip=20 (default)   | byte   | 11.29 s   | 89.0%    | 2.48      | 27%     | 25%        | 48%       |

The real ROM runs fewer instructions per second (they take more cycles on
average), but about the same emulated speed as the synthetic loop when
byte-compiled.  Native compilation helps it more (1.9x on the CPU core
vs 1.4x), and the overall picture is the same: drawing and the input wait
take more than half the time.

** Takeaways

- Once compiled, emulation is less than half of the wall time.  The rest is
  drawing (~100 ms per drawn frame) and the 0.1 s key-read timeout, which
  waits the full 100 ms on every drawn frame when no key is pressed.
- With default frame skipping the game runs at about real speed but only
  shows ~2.6 frames per second.  Drawing every frame gives under 5 fps.
- Native compilation helps the CPU core (~1.5x) and building the frame text
  (~2x), but barely changes redisplay or the wait, so it's only about 10%
  faster overall.
- The first targets are clear: the input wait (~30–50%), then redisplay and
  building the frame text.

* Frame pacing instead of the 0.1 s key wait

=eboy-debug-update-fps= no longer waits up to 0.1 s for a key after every
drawn frame.  New =eboy-pace-and-read-keys=: it only waits when the
emulator runs ahead of a real Game Boy, for exactly that long, and that wait
still returns at once on a key press; otherwise it just checks for a key.
=eboy-limit-speed= (default =t=) turns the speed limit on or off.

Keys work as before (checked by feeding =s= and =k= into a running ROM: the
joypad registers changed to A and down), and a press lasts until the next
drawn frame, as before.  Blargg: all tests still pass.

The benchmark now turns the speed limit off for the =full= rows, to measure
how fast it can go, and adds a =paced= row as a player runs it.  Raw output:
[[file:bench/results-frame-pacing.txt][bench/results-frame-pacing.txt]] (CPU-only and render rows unchanged, as
expected).  Measured on top of the bug fixes; a first measurement on top of
fe04bd5 gave the same picture.

Blargg "10-bit ops" ROM, compared with the new baseline (after the bug fixes):

| Run                   | Mode   | Baseline GB speed | Now GB speed | Baseline drawn fps | Now drawn fps |
|-----------------------+--------+-------------------+--------------+--------------------+---------------|
| skip=20 (default)     | byte   | 91.5%             | 123.2%       | 2.55               | 3.43          |
| skip=20 (default)     | native | 124.8%            | 158.7%       | 3.48               | 4.42          |
| skip=0 (every frame)  | byte   | 7.7%              | 14.7%        | 4.59               | 8.79          |
| skip=0 (every frame)  | native | 8.4%              | 15.7%        | 5.05               | 9.35          |
| skip=20, speed limit  | byte   | -                 | 101.7%       | -                  | 2.83          |
| skip=20, speed limit  | native | -                 | 98.6%        | -                  | 2.75          |

(The synthetic workload shows the same picture: skip=20 native 114.5% ->
152.0%, skip=0 native 5.04 -> 9.62 fps.)

- Drawing every frame is now about *1.9x faster* (byte and native), because
  the wait was nearly half of the time there.
- With default settings it is 27–35% faster.  With the speed limit on it
  holds real-time speed (99–102%) and is idle 18% (byte) to 27–33% (native)
  of the time: room that could go into drawing more frames.
- What's left: drawing is now 91–93% of the time when drawing every frame, so
  the renderer and redisplay are the next target for frame rate; the
  emulation itself (~60% with default settings) is the next target for speed.
